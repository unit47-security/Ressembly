# Ressembly audit · October 24, 2026

This report records the state of the project and the test environment on the audit date.

## Local findings

The README and SUITE-UNIT47 were read first. No AGENTS instructions were found in the project or its parent directories. The working directory was not a Git repository. The audit did not check for external repositories.

Before the changes, `src/ressembly` and `examples` were empty. The project contained five HTML, JavaScript, and CSS prototype files, JavaScript tests, and seven documents. The comparison engine reads imported function-entry records for the same build and scope. It checks declared hashes, ordering, references, and partial data. The interface labels its examples as synthetic. The prototype does not collect debugger events. A static search found no uses of fetch or XMLHttpRequest in the prototype. The audit did not assess security comprehensively. All 14 historical tests passed on a fresh run. Browser interaction tests were outside this audit.

SPECIFICA, APP-DESKTOP, ROADMAP, and BACKLOG already marked the Windows/Qt proposal as historical. CONFRONTO and VERIFICA needed clearer links to the current direction. The prototype files were retained.

The audit environment was Darwin 25.3.0 on ARM64 with Apple clang 17.0.0, Python 3.9.6, and Node available. GDB, Docker, Podman, Colima, Lima, and QEMU were absent from PATH. A Linux x86-64 environment was unavailable for this session. The audit required no dependency installations or global configuration changes.

## Classification of findings

- **Verified locally:** The offline demo and JavaScript comparison engine tests.
- **Documented by primary sources:** The tool capabilities listed in the CONFRONTO matrix. No benchmark was run for this finding.
- **Reproduced in the project or environment:** The project had no GDB collector before this work. GDB could not be launched from PATH in the audited environment.
- **Still unverified:** Competing tool bugs, coverage gaps, time savings, overhead, and usability advantages. The audit attributed no bugs to GEF or Pwndbg.
- **Hypothesis:** Generation-based identities and readable provenance may make reconstruction easier. The audit established neither novelty nor superiority.

## R1a implementation decision

R1a uses a narrower scope than R1 and R2. It calls for a project-owned C fixture with explicit markers and no intentional undefined behavior, a GDB Python extension independent of GEF, bounded marker and snapshot collection, and an offline model for allocation identities and address reuse. Reports are available as JSON and in the terminal.

Markers record what the program declares after selected operations. Coverage is limited to those declarations and the sampled values. The collector does not intercept malloc or free automatically or inspect glibc metadata. A difference between snapshots establishes a change between the observed values. The number, instructions, and order of intervening writes remain unknown. Writes that leave the value unchanged and changes reversed between observations may be absent. The report contains no vulnerability or exploitability verdicts.

Local acceptance called for offline core tests, compilation and execution of the C fixture on the Mac, a repeatable script prepared for Linux x86-64, and a clear separation between synthetic test data and real captures. **Operational acceptance was still open on the audit date.** It required running the script on Linux x86-64 with Python-enabled GDB, retaining versions, hashes, logs, and JSON, and checking the markers and bytes directly in GDB. Completing R1 required that validation.

R0 also remained partial on the audit date. The documentation review was complete, and benchmarks across three lab environments and the associated checks were pending. The plan called for testing the actual comparison workflows before introducing intentional use-after-free or overflow cases.
